# SECURITY.md: Phase 8 security pass

Scope: everything in `916-dent-detail/` as of the Phase 8 commit. Method: secrets scan of the working tree and git history, `npm audit`, review of every
API route, executable RLS tests (all migrations applied to an in-memory Postgres, PGlite), and targeted tests for each fix. Each `0005` fix was checked the hard way: with `0005_security_fixes.sql` removed, five of the PGlite assertions fail; with it, all 29 pass.
**Limits of this review:** nothing was run against real Supabase, Stripe, Twilio or Resend (no keys, no accounts, by rule). This is a code and
policy review plus automated tests, not a penetration test. Items marked "needs a live check" are on the launch checklist.

## Reviewed and found sound
- **Secrets:** `git grep` over the tree and `git log -S` over history for Stripe/Twilio/AWS/Anthropic/Google/GitHub/Slack/Resend key shapes, private keys and JWTs: no real secret. `.env.example` is empty-valued; `.env*` is git-ignored. The only match is a fake `sk-ant-…` string inside a test of the output secret-filter.
- **Webhook authentication:** Stripe (three endpoints) verifies `constructEvent` with the raw body and its own secret; Twilio verifies HMAC-SHA1 over URL + sorted params with constant-time compare and is refused (503) when Supabase is live but Twilio is not configured; cron routes use a constant-time bearer compare and answer 503 in production without `CRON_SECRET`.
- **Token expiry:** booking links (HMAC-SHA256, exp), chat sessions (30 days, exp), dealer sessions (12 h), admin sessions (7 days, role re-read from the database on every server request in live mode, so a revoked role takes effect immediately). Tampered, expired, malformed and extra-segment tokens are rejected (`booking.test.ts`, `auth.test.ts`, dealer tests).
- **SSRF / open redirect:** every server-side `fetch` targets a fixed host (Twilio, Resend, Google, Meta, Upstash, the Twilio MMS host which is pinned to `api.twilio.com` over https). Post-login redirects go through `safeNext` (same-site `/admin/…` allow-list). The only other redirects are constants or Stripe-issued checkout URLs.
- **Uploads:** magic-byte image check (JPEG/PNG/WebP only), size cap, server-generated storage paths (client filenames and types are never used), strict path regexes on every read route, private bucket + authorization check + short-lived signed URL for staff, dealer ownership check for dealers.
- **Input validation:** every JSON route parses with zod and a byte cap; unknown keys are rejected on bot tools; bot output is filtered (prices, URLs, PII, prompt/tool leakage) and all tool authorization is enforced server-side (`tests/bot/adversarial.test.ts`).
- **Rate limits:** every unauthenticated POST route is limited per IP (in memory, or Upstash when configured); admin routes 240/min per user; auth routes 5-10 per 10 min; bot per IP, conversation, phone and cost.
- **Auth boundaries:** `src/proxy.ts` gates `/admin` and `/api/admin`, handlers re-check; demo logins are off whenever Supabase is configured and in production unless explicitly enabled (`doctor --production` fails if enabled); the bot's demo verification code `424242` is never accepted with Supabase live.
- **RLS (executable):** `tests/unit/rls-pglite.test.ts` applies migrations 0001 to 0005 and `seed.sql` to PGlite, then asserts for anon, a signed-in stranger (customers have no accounts), owner, admin, two technicians and two dealers who may read and write what. It also asserts that every table has RLS on, the exclusion constraint prevents double booking, and the webhook-idempotency indexes hold.
